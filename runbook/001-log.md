# H-01 — the spine

Docker, a reverse proxy with automatic HTTPS, and a wildcard cert on names that
resolve to a Tailscale address.

## 2026-08-30
- **Did:** Delegated `lab.akhildhyani.me` to deSEC with two NS records at Namecheap,
  leaving the apex, Vercel and the email forwarding untouched — Namecheap's own API is
  gated behind spend thresholds a Student Pack domain can't meet, and Cloudflare's free
  plan won't take a subdomain as its own zone. Docker + Compose v2 from the upstream apt
  repo (`40-docker.sh`), json-file logs capped at 3 x 10M because the default never
  rotates. Caddy built with the deSEC DNS module, wildcard cert for
  `*.lab.akhildhyani.me` over DNS-01, ports bound to `100.94.219.53` explicitly because
  Docker's iptables rules run ahead of ufw and a bare publish would have opened 443 on
  the campus LAN. `whoami` loads with a real padlock from cipher and from the phone.
- **Broke:** DNS-01 failed four times with "No TXT record found". Not the token and not
  the delegation — deSEC's ns2 replicates ~60s behind ns1 (measured: ns1 at 13s, ns2 at
  71s) and Caddy submitted the challenge within 9s, so Let's Encrypt's secondary vantage
  point queried a nameserver that hadn't caught up. `propagation_delay 150s` fixed it.
  Then the phone: Android permits one VPN at a time, so WARP and Tailscale cannot coexist
  there, and Android's Private DNS in strict mode kills all resolution once Tailscale
  installs MagicDNS. Turning Private DNS off fixes it; the better fix is turning off
  "Use Tailscale DNS settings" in the Tailscale app, which keeps DoT working and still
  resolves the lab — because the lab names are public DNS records, not MagicDNS names.
  That is an argument for the naming scheme, found by accident.
- **Differently:** Measured the replication lag with a throwaway TXT record written
  straight through the deSEC API, instead of guessing from Caddy's retry cycle. Should
  have done that at the first failure, not the fourth.

## 2026-08-30 · second session
- **Did:** Ran the first real reboot test on the H-01 stack, which failed, and spent the
  rest of the session on what it exposed. Two fixes into the repo: `ip_nonlocal_bind=1`
  in `40-docker.sh`, and a new `05-hw-quirks.sh` turning off both of the wifi card's
  power-saving states. Validated on a cold boot: 19.3 s, `wlo1` associating unattended
  and carrying the box alone, `tailscale0` and `caddy` both up on their own with ports
  bound, no failed units, `whoami` serving over HTTPS.
- **Broke:** Four separate faults, in the order they surfaced. **(1)** Caddy exited 128 at
  boot — it publishes on `100.94.219.53`, which does not exist until tailscaled registers,
  and because that is a *start* failure rather than a crash the `restart: unless-stopped`
  policy never retried. **(2)** The campus wired wall port silently stopped passing HTTPS:
  ICMP, DNS, HTTP/80 and every packet size up to 1472 fine, TCP/443 blocked to most
  destinations, no captive portal. Campus wifi unaffected. Not ours to fix, and it is what
  made the box look dead. **(3)** The RTL8822CE storms uncorrectable PCIe `CmpltTO` errors
  the moment wifi carries traffic alone — fast enough that the console cannot be typed on
  (`sudo dmesg -n 1` blind is the escape hatch). It needed *both* `disable_aspm=1` for the
  PCIe link and `disable_lps_deep=1` for the radio; fixing only the first left it logging
  "firmware failed to leave lps state". **(4)** `disable_lps_deep=1`, added to
  silence (3)'s remaining "failed to leave lps state" messages, made it far worse: the card
  associates, runs ~30 s, then storms `failed to send h2c command` and ends at `mac power
  on failed`, wedged in D3cold with `Unable to change power state from D3cold to D0` and
  probe failing `-114`. Only a full power-off recovers it. Reverted. **ASPM alone is
  correct**: a later cold boot and a later warm reboot both came up with zero rtw88
  errors, and a 14-minute soak pulling ~950 MB over wifi logged none either.

  *Corrected after first writing this entry:* I logged the warm reboot as a hard failure
  and wrote "wifi does not survive a warm reboot" into CLAUDE.md. Wrong — wifi simply
  takes ~169 s to finish WPA2-Enterprise association, and I checked at 14 s.
- **Differently:** Spent half an hour guessing at the campus firewall through one-line
  `curl` tests read off photographs, when tethering MAGI to a phone would have separated
  "MAGI is broken" from "this wall port is broken" in two minutes. Reach for the
  known-good network first, then diagnose.

## 2026-08-31
- **Did:** Root-caused the wall port, which was never a policy block. It is a 24online
  walled garden: a Webcat/Skein proxy answers every HTTP request with a login page, and
  TCP/443 is refused outright until you authenticate — so an unauthenticated wired link
  looks exactly like a dead network, with DHCP, DNS, ICMP and every packet size fine. It
  worked all day on a session established before, and died at the first reboot when the
  lease changed. `35-netaccess.sh` now logs in over HTTPS and a systemd timer re-checks
  every two minutes, acting only when 443 is actually shut, because the session is bound
  to the DHCP lease rather than to the boot. Then ran the full test matrix: wifi soak
  (950 MB / 14 min), cold boot, warm reboot, wall port, failover, and an unattended reboot
  on wired — all six green, zero rtw88 errors, back in 12 s.
- **Broke:** The portal login failed four times, each for a different reason, and only the
  last mattered. The bare username is rejected — the page's own JavaScript appends
  `@iitj.ac.in` before submitting. The GET and the POST ran as separate curl invocations
  so the servlet's `JSESSIONID` never came back. Redirects weren't followed. And the real
  one: **every plain-HTTP POST is 302'd to the servlet's own `https://` URL with an empty
  body**, so the login silently did nothing regardless of credentials. The walled garden
  permits 443 to the portal host itself, and its certificate validates, so posting
  straight to HTTPS works. Separately, two things I called fixed were not: a 45-second
  sample said the wifi card was healthy when it was already failing at 30 s, and "wifi
  does not survive a warm reboot" was wrong — it needs ~169 s for a first PEAP association
  and 10.5 s once the PMK is cached. I had checked at 14 s.
- **Differently:** Debugged the portal by changing one thing and re-running blind, four
  times. Dumping the response headers first — which found the 302-to-HTTPS immediately —
  should have been step one, not step five. Same shape as the earlier lesson about
  reaching for the tether: look at what the thing actually says before theorising.
